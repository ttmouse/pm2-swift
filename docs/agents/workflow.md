# 开发工作流规则

## 五阶段开发流程

每个功能开发必须遵循以下结构化流程：

### 阶段 1: 需求分析
- 明确功能的目标和边界
- 确定影响范围（哪些文件会被修改）
- 检查是否与现有功能冲突
- **输出**: 清晰的变更描述

### 阶段 2: 设计
- 确定架构层级归属（Model/Service/View）
- 定义接口签名（方法名、参数、返回值）
- 评估是否需要修改协议（`PM2ServiceProtocol` / `ConfigPersistence`）
- **输出**: 实现方案概述

### 阶段 3: 编码
- 遵循 `.qoder/rules/` 中的编码规范
- 不引入未在设计中讨论的变更
- 为关键逻辑添加注释
- **输出**: 实现代码

### 阶段 4: 自审
- 逐项检查质量门禁（见 AGENTS.md Review 节）
- 验证 IPC 格式正确性
- 确认无强制解包
- **输出**: 自审后的代码

### 阶段 5: 验证
- `./build.sh` 编译通过
- `xcodebuild test` 测试通过
- 如有冒烟测试，验证功能表现
- **输出**: 可交付的代码

## 规则

### 编码规则
1. **一次只做一件事**: 一个 PR/提交只解决一个问题
2. **不要过度工程**: 不添加未要求的抽象层、配置项、错误处理
3. **不要破坏现有测试**: 修改代码前先运行测试确保 baseline

### 评审规则
1. 编码 Agent 和评审 Agent 必须分离
2. 同一问题最多 3 轮往返，超过则人工介入
3. 每轮评审必须输出明确的通过/拒绝结论

### 变更追溯
1. 每次 AI 驱动的功能变更必须在 `.qoder/changelog/CHANGELOG.md` 中记录
2. 记录格式见 CHANGELOG 模板
